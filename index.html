Draw your application. Run it on your own servers.

Connect modules such as a gateway, NGINX and PostgreSQL on a canvas. Apelora turns each connection into an access rule and a service address, runs the result on your Linux servers, and keeps it running.

Get the source on GitHub See what works today

Open source under AGPL-3.0. Early development: tested on a four-server lab, not ready for production.

Stop hand-writing the network between your services

For platform and operations engineers at teams that run their own Linux servers. If you keep container, network and firewall files in step by hand, this replaces that work.

Connections become rules

Only the connections you draw are allowed. Each one gets an access rule, and the module you connect to gets a stable service name and address inside the application's own network.

Impossible links are refused

The designer rejects what cannot work, such as HTTP into a database port, before anything is deployed. The control plane then checks the design against your cluster.

Failures are handled

Replicas run on different servers, unhealthy ones are restarted, and lost ones are replaced. A stateful module restarts on another server only after its failed server is fenced.

From a drawing to running instances

Three steps. Each one is a separate piece you can read, test and replace.

  1. 01

    Design

    In Apelora Studio, drag modules onto the canvas and connect their typed ports. A catalog of 83 modules in 12 categories comes with it, and you can define your own.

  2. 02

    Deploy

    The control plane plans the change and shows it first. The deployment worker then creates each module's instances (containers or virtual machines) in Incus as durable jobs, so a crash or a repeated request never creates duplicates.

  3. 03

    Operate

    Replicas are spread across servers, health is checked, and recovery is decided by one supervisor at a time. Everything that changes is written to an append-only audit log.

Built on Incus, not instead of it

Apelora owns the application: its design, desired state, connections, replicas and health. Incus owns the servers: cluster membership, placement and the instances themselves. Apelora talks to Incus only through its documented REST API, with TLS verified.

  • Three kinds of module. System containers, application containers and virtual machines, as each module's class says.
  • One network per application. Deny-by-default rules compiled from your connections, with service discovery and optional internet access.
  • Your storage. Local disks today, with backups to another pool. Clustered storage on a SAN lets a module restart on another server.
  • Your servers stay yours. Credentials for Incus, for management controllers and for MAAS stay in the backend, never in the browser.

Run it from the Fabric Console

The administrator's view of the cluster: what is running, what is failing and who changed what.

  • Servers. Database majority, members, failure domains, maintenance with evacuation, and joining new servers with single-use tokens.
  • Health. Control plane, database, workers, job queue and servers, each in words with its reason.
  • People and approvals. Roles at organisation, project and application scope, with a second person's approval for sensitive changes.
  • Audit. Who did what, to what, and whether it was allowed; searchable and exportable.
  • Alerts and metrics. Fifteen built-in rules and a metrics endpoint for your own monitoring.
  • Backups and restore. Volume backups, scheduled snapshots, and a restore that takes a safety backup first.

Try the designer in a minute

The Studio runs in your browser with sample data and deploys nothing. It needs Node.js and a clone of the repository.

git clone https://github.com/Apelora/apelora-fabric.git
cd apelora-fabric
npm install
npm run dev   # Studio at http://127.0.0.1:5173

To deploy for real you need Incus servers, and you do not need to buy any: a disposable cluster of virtual machines on a Mac or Linux workstation stands in for them. Testing without hardware explains what that lab proves, and what only real servers can prove.

Open source, written in the open

Apelora is licensed under the GNU Affero General Public License, version 3 only (AGPL-3.0-only). The control plane is Rust and PostgreSQL; Studio and the Fabric Console are React. Design decisions are recorded as short documents, and operating procedures are written as runbooks.
