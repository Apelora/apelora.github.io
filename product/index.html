Apelora Fabric has two screens and one control plane. Studio is where you design; Fabric Console is where you operate. Every result here says how it was checked.

Design

Apelora Studio is a canvas for connected modules. Ports are typed, so a cable that cannot work is refused.

  • A catalog of 83 modules in 12 categories, and modules you define yourself.
  • Import and export designs as files; undo and redo.
  • Deploys today: NGINX (an application container), Debian (a system container) and a Linux virtual machine. The other 80 modules are design-only until their images have run on the lab.
Checked in a real browser

Plan and deploy

Before anything changes, Fabric shows what would be created, resized or removed, and whether it fits your servers.

  • Containers and virtual machines, one per replica, with CPU and memory limits.
  • Volumes that outlive their instance: grow online, snapshot, back up to another pool, restore.
  • Resize running instances in place, and move an instance to another server (virtual machines move live).
Real Incus tested

Connect

Cables become network policy. Each application gets its own network, and only the connections you drew are allowed.

  • Deny by default, with an access rule for each cable.
  • Service addresses with health checks; a gateway connection publishes a module.
  • Each module is told its providers' addresses. Internet access is optional, per module.
Real Incus testedService names (DNS): roadmap

Recover

Failed replicas are restarted or replaced. For a module that keeps data, Fabric fences first, then restarts.

  • Fenced means proven stopped: its storage lease is dead, its power is confirmed off, or a person confirms it. Two servers never write the same disk.
  • A container with data ran again 144 to 155 seconds after a forced stop, in three lab drills.
  • A server cut off but still running was switched off through its management controller and fenced after 61 seconds in the lab. That does not make the restart faster on this storage.

Operate

Fabric Console, in your browser.

  • Servers, maintenance with evacuation, joining and removing servers, and cluster settings with a dry-run review.
  • Instances with logs and terminals; operations you can retry or cancel; networks and storage.
  • Applications start, restart and stop in dependency order, with a warning when clients would lose service.
Real Incus testedTerminals: checked against a stand-in

Secure

Access is explicit, and every change is recorded.

  • OpenID Connect, LDAP and local sign-in; roles at organisation, project and application scope.
  • A second person approves sensitive changes. A token can never grant more than its creator holds.
  • An append-only audit log, searchable and exportable. Credentials stay in the backend, never in the browser.
Checked with test identity serversNot independently audited

Monitor

Know before your users do.

  • 16 built-in alert rules (failed jobs, silent workers, offline servers, expiring certificates, failed backups) with signed webhooks.
  • A metrics endpoint for the control plane and the worker, for your own monitoring.
  • A support bundle with versions, health and failed jobs; secrets are never included.
Checked against stand-ins and a real database

Roadmap: what is not built, or not yet tested.

We would rather tell you now. Each item is in the repository's status document with its current state.

ItemStateWhat it means for you
Production useNot yetTested on a four-server lab of virtual machines; no real servers have run it, and speed and scale are unmeasured.
Virtual machines after a server diesPlannedContainers with data on shared storage recover; virtual machines are not drilled.
Operating systems through MAASNot builtDiscovery and registration of MAAS machines is built and tested against a real MAAS; installing an OS through it is not. Servers installed by hand join with a token.
Management controllersPartly builtA Redfish fence provider exists, tested against a test server only; IPMI is not built.
More deployable modulesOngoingThree of 83 modules deploy; each new runtime is added after its images have run on the lab.
Rebalancing and staged upgradesNot builtInstances are not moved automatically for balance; the rolling Incus upgrade is a written procedure, not an assistant.
Service names (DNS)Not builtModules find each other through addresses injected as settings.
Several sites and regionsDesignedA design from three servers to a global fabric is written down; the multi-site parts are not built.
Remote desktop sessionsNot builtTerminal sessions exist; remote desktop does not.

Words used on this site.

Module
A building block on the canvas, such as a web server or a database, with typed ports.
Instance
A running container or virtual machine that a module becomes. A module with three replicas becomes three instances.
Incus
The open-source system that runs containers and virtual machines across a cluster of servers. Fabric builds on it and does not replace it.
Fenced
A failed server is proven stopped, so it cannot write to shared storage while its modules restart elsewhere.
Replica
One of several identical copies of a module, run on different servers.
Runbook
A written procedure for a situation such as a failed server, with each step marked as tested or not.
