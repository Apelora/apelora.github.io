    When something goes wrong

    Start with Health in the Console, then open Operations for failed jobs and Audit for what changed. Running instances are not affected by Apelora being down: Incus runs them and Apelora is not in the data path.

    Which runbook

    SymptomRunbook
    A server is downA server fails
    The cluster cannot reach a majorityThe cluster loses quorum
    A replica fails its health checkA replica fails its health check
    The Console or Studio cannot reach the APIThe control plane or the worker is down
    A pool is filling up, or backups stoppedA storage problem
    Applications cannot talk to each otherNetwork incidents
    A deploy fails, or a job keeps failingTroubleshooting with logs and the audit trail
    A certificate is about to expireRotate Apelora's Incus certificates
    A stolen token or misused accountA security incident
    You need to service a serverMaintenance on a server

    When a server fails

    Incus marks it offline after about 20 seconds. Stateless replicas are replaced on other servers after a delay. A module with data on shared storage restarts elsewhere only once the failed server is fenced: proven stopped, so two servers never write the same disk. In the lab a container with data ran again 144 to 155 seconds after a forced stop. A server fails has the timeline, what is automatic and what is not, and what has not been tested. Every runbook states which of its steps were.

    Looking after Apelora itself

    Back up and restore its database: Back up and restore Apelora's own database. Upgrade Incus without downtime: a rolling Incus upgrade. Update without internet access: offline update. All runbooks: Runbooks.
