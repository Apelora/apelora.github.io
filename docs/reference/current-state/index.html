    What exists and works

    The parts of an application are called modules (formerly appliances; ADR 0006). Designs, API requests, stored records and Incus labels written before the rename are still read. Illustrations: platform layers, from a design to running instances, storage layers.

    Earlier design

    An earlier hypervisor-based design (a Rust node agent and a VM per module) was never built and was replaced by ADR 0001. Its documents and skill were removed on 2026-10-20; skills, agents, README, CLAUDE.md, SECURITY.md and the commercial licence drafts describe the Incus-first platform.

    What carries over unchanged

    • The whole Studio app and both packages. The Incus runtime is an addition to a module class (Phase 06), not a change to existing documents.
    • Port/terminal model, catalog rules, port placement convention, visual design contract.
    • Licence: AGPL-3.0-only for our code. Incus (Apache-2.0) and MAAS (AGPL-3.0, if adopted per ADR 0002) are used over their APIs.

    Known limitations

    • Incus 7.0.2 is what the lab runs. The LTS package 1:7.0.2-debian13-202610211947 was installed on all four members on 2026-10-23 (stand-by, then the other voters, database leader last). The first upgrade blocked the other three until they ran the same release; afterwards every member was Online on 7.0.2, with three database voters and one stand-by. The cluster was empty, so nothing was evacuated. Earlier evidence was produced on 7.0.1.
    • OVN HA and TLS (issue #13): scripts/test-cluster/ovn-ha.sh converts the lab's one database into three clustered northbound/southbound databases with TLS (APPLY=1, 2026-10-22, four members, OVN 25.03). REAL INCUS TESTED: raft had three members; stopping the leader's ovn-ovsdb-server-nb/sb elected another (term 3); 15 OVN ACLs on apelora-default were unchanged; Incus still listed 30 leftover module ACLs over ssl: remotes; a Debian container on that network pinged the OVN router (10.13.53.1) 5/5 with 0% loss during the outage. ovn.sh still starts the single-node plaintext shortcut.
    • One architecture (aarch64) on the test cluster: no mixed-architecture evidence.
    • IPv6: application-network rules and IPv6 service addresses (fd42:198:100::/112 on ipv6.routes) REAL INCUS TESTED 2026-10-22 (ipv6.sh). The servers' own cluster addresses stay IPv4. Do not set ipv6.address on the lab's NAT incusbr0 (it wedged network create until incusd was SIGKILL-started).
    • Member failure: OVN health checks cannot see a dead member, so a service address keeps sending a share of requests to its replicas there until Apelora substitutes them (APELORA_RECOVER_AFTER_SECS, default 120 s). Single-instance and stateful modules are recovered automatically only when all their disks are on the shared pool, and only after their member is fenced (about 140 s after its last lease renewal; ADR 0013); on member-local pools they wait for their member.
    • Publishing needs the network outside to route service addresses to the application network's router; the OVN router does not answer ARP for them.
    • Service names (DNS) are delivered with the service address (APELORA_SERVICE_NAME_<PROVIDER> = <module>.<application>.internal) and published on the application network. REAL INCUS TESTED 2026-10-23 (dns.sh) for the publication. The optional resolver module answers the names inside the application and forwards the rest. REAL INCUS TESTED 2026-10-23 (dns.sh): the restarted client resolved the service name to the service address, and the instance name still resolved. Without the module, OVN's own DNS still answers instance names only. An instance created earlier keeps the environment, and the DNS servers, it was given at boot (ADR 0004).
    • Resources apply when an instance is created, and a later deployment resizes CPU and memory in place (instance.resize, REAL INCUS TESTED on a running container). Disk size is a separate volume grow. VMs, and a limit above the project's quota being refused by Incus, are not tested.
    • Health is Incus status plus the load balancer's TCP port check, with hysteresis; an application that hangs behind an open port is detected only for a module that declares a readiness command, and instances without a service address are not checked. Health trackers live in the worker's memory: after a worker restart they start over.
    • Load balancer quirks (Incus 7.0.1): updates may be refused while a member is down — in one drill for the whole outage (retried; the substitute joins once they succeed) — and may drop the OVN health check (detected through the state endpoint and re-applied).
    • Offline detection: in one drill Incus briefly reported a member that was not stopped as Offline; keep the recovery delay well above that (default 120 s).
    • Bare-metal provisioning (Phase 09): servers installed by hand are enrolled, held and admitted through Apelora; the MAAS adapter lists machines, fences through MAAS, and can commission and install an OS (cloud-init is sent and not stored). Commission, install and release are CONTRACT VERIFIED only, not REAL MAAS TESTED. Disk erasure on release is off unless asked. A secure wipe is not offered. Burn-in runs MAAS's hardware tests and feeds admission (CONTRACT VERIFIED; no test run on real MAAS or hardware). An unreachable member is not removed through Apelora (Incus can only force it; see the runbook). Incus cannot hold a member before it joins, so the enrolment script holds it right after the join; a member that joins another way is flagged, not blocked.
    • Health and capacity (2026-10-21): the page shows the present only (no history or alerts yet); identity providers are reported from the control plane's last check, not probed per read; the per-server instance list covers only the projects Apelora's Incus identity may see; the Studio's capacity fit is advice (Incus reserves nothing for limits; root disks are not counted).
    • Releases: v0.1.0-alpha.1 exists as a draft release (artefacts and checksums built by the release workflow). The staged file upgrade and its file rollback are tested (scripts/ops/upgrade.sh); stopping the units and restoring the database are NOT YET VERIFIED. Example systemd units and the NGINX configuration (infra/systemd/, infra/serve/) are parsed in CI and were started on one lab member from that draft (install-units.sh, 2026-10-23: both units active under apelora, health connected to Incus 7.0.1, Studio and Console 200). Issue #17 stays open until a published release on a production host.
    • Several sites: one site and one sector, named on Servers → Members. A second deployment in another site is refused until another site is connected. No second Incus cluster, no network between sites, no move between sites.

    Deviations from the incoming specification (deliberate)

    • npm workspaces kept instead of pnpm (owner decision): no tooling churn; Fabric Console is another workspace.
    • Crates created when first needed, not all at once: Phase 01 adds crates/domain and crates/incus-adapter plus the two services; the other planned crates are listed in the architecture but created by the phase that gives them code.
    • No other product names in repository text (rule 9); the incoming documents were rewritten in our own words and the files/ drop folder removed.
    • No gradients in UI themes (design rule 5), although the incoming spec mentions gradient themes.
    • Repository stays Apelora/apelora-fabric (the spec says Apelora/apelora).
