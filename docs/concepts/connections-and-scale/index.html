    Connections between layers, and how far Apelora scales

    Status: reference · Date: 2026-10-21 · Decision: ADR 0008 — sectors · Layers: platform architecture

    This page lists every connection between the layers of an Apelora installation — who opens it, over what, how it is authenticated and what happens when it breaks — and then how far each layer scales, with the source of each number. Numbers marked estimate are ours; the others come from the upstream projects.

    1. What runs where

    LayerRuns onInstances of it
    Fabric Console, Studiothe person's browser (static files served next to the API)any
    Control plane (API)one or more Linux hosts or containers outside the clusters it manages1 today; several behind a load balancer once the per-process state below is shared
    Deployment workersameseveral (jobs are claimed with leases) — except the replica supervisor, see §4
    PostgreSQLa managed or self-run PostgreSQLone primary, optional replicas
    Incusevery physical server in a cluster (a member)one cluster per sector (ADR 0008)
    ModulesIncus instances on the members: LXC system containers by default, OCI application containers where the module class asks for one, virtual machines only where needed (another kernel or OS, kernel modules, live migration)replicas of one module are separate instances, usually on different members
    OVN (when used)central databases on members of the same cluster; ovn-controller on every memberone OVN deployment per sector
    Shared storage (when used)a SAN (iSCSI, Fibre Channel or NVMe over Fabrics) reachable from every member of the sectorone shared volume group per pool

    In the disposable test cluster, Lima virtual machines stand in for the physical servers; nothing in Apelora depends on that.

    5. Beyond one cluster: sectors linked into one fabric

    A sector is one Incus cluster: one site, at most about 50 servers, its own cluster database, its own OVN and its own storage pools. The fabric is all sectors together. Decision and details: ADR 0008. Past a few hundred servers, or across countries and continents, sectors are grouped into sites and regions, each region with its own control plane: global fabric and ADR 0009.

    LinkConnectionWhat it givesNeeds
    Management8 and 9, once per sectorone Console, one audit log, one set of people and roles; inventory, health and capacity across sectors; placement chooses a sectorthe sector's Incus endpoint and its restricted and administrative certificates
    Network18 — OVN interconnection between the sectors' OVN deployments (TCP 6645/6646 to the interconnection databases; Geneve between gateway members)a module in one sector calls an application in another over a peered, routed network; ACLs still allow only what was drawnan interconnection database shared by the linked sectors, gateway members, one certificate authority for OVN, non-overlapping subnets (Apelora allocates them per sector)
    Data19 — Incus migration between clusters (HTTPS 8443)copy or move instances and volumes between sectors, as a job with a dry runpools, networks and profiles with the same names in the target sector
    Recovery19 — backup copies to another sectorredeploy a lost sector's applications elsewhere from desired state and the latest backupsa backup pool in the other sector
    • An application is placed in one sector; its replicas stay inside it (they share an application network and, for stateful modules, storage).
    • For availability across sites, the same application is deployed to two sectors and published behind one address (DNS or an external load balancer); data is replicated by the application (database replication), not by Apelora.
    • People see one Console: servers, health and capacity are grouped by sector; the Studio asks for a sector only when there is more than one.
