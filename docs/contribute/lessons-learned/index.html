    Lessons learned

    What went wrong while building Apelora, why, and the rule we follow now. Every coding agent reads this before starting a task (AGENTS.md says so) and adds an entry when something fails for a reason that was not obvious.

    How to use this file

    • Before a task: read the sections that touch your area. The rules here come from real failures.
    • Add an entry when a check fails for a non-obvious reason, when a real system behaves differently from the mock or the documentation, when the owner corrects how we work, or when a fix needed more than one attempt.
    • Entry format: one bullet, **What happened** → cause → rule now, with the date (YYYY-MM-DD) and, where useful, the file or test that now guards it. Keep it to three lines.
    • Keep it useful: merge duplicates, and when a rule moves into code, a test or a skill, shorten the entry to a pointer. Delete entries that no longer apply.
    • Review it at the end of each phase: look for repeated causes, which mean a process or tooling gap. Fix the gap, not just the instance.

    Patterns so far

    Read these first. Most entries below come from one of four causes:

    1. The mock or stub was kinder than the real thing. It answered instantly, had no limits and never failed. Model latency and limits in stubs, and test against a real local system before calling something done.
    2. A failure was silent. Nothing in the logs or on screen said why. Every refusal and swallowed error gets a log line with identifiers, and the UI shows the server's reason.
    3. Check the result, not the step. Wait for the observable result (an instance's location changed, the page shows data), not for "the job finished".
    4. Environment differences between macOS and Linux, development and production builds, and mouse and touch input.

    Front end and browser

    • The provider's sign-in code was exchanged twice in development and the sign-in failed (2026-10-21) → React StrictMode runs mount effects twice. The second run found the pending sign-in already used, failed, and triggered a request with no token. → Do one-shot side effects (code exchange, one-time tokens, POSTs on mount) once per page load through a shared promise (finishOidcSignIn in apps/fabric-console/src/App.tsx). Guard: the e2e test delays the token endpoint by 400 ms and expects exactly one exchange.
    • Stubbed tests passed while the real flow failed (2026-10-21) → the stub answered at once, so the race never happened. → Give stubs of external services realistic latency, and finish UI work with one run against a real local service (infra/dev, profile oidc).
    • "Your session ended" when the real cause was a refused token (2026-10-21) → the UI picked a generic reason. → Show the server's message when the cause is not the obvious one (fromProvider in App.tsx).
    • A Playwright test's second goto to another hash did not reload the page → hash-only navigation keeps the old route stubs and state. → Use separate tests for separate stub setups, or page.reload().
    • A stubbed identity provider failed in the browser → no CORS headers. Real providers send them for registered origins. → Stubs of cross-origin services send access-control-allow-origin.
    • Row actions pushed Delete off screen at 390 px; 24 px buttons in measurements → no wrapping, and the measurement ran without touch emulation, while the console makes controls 44 px on coarse pointers. → Use flex-wrap justify-end for action groups, and measure phones with isMobile and hasTouch on.
    • Screenshots caught dialogs mid-animation; Ctrl+click did nothing on macOS → use emulateMedia({ reducedMotion: "reduce" }) and ControlOrMeta.
    • The Studio showed the generic "saved sign-in was not accepted" after a refused provider token (2026-10-21) → two places ran the same detection, and the one that did not do the exchange reported last. → Keep facts about the page load (which token the provider issued) at module level, not in one call's local variable (providerToken in apps/studio/src/features/applications/backend.ts).
    • A docs agent captured screenshots while the same page was being redesigned in the main checkout (2026-10-21) → parallel work on one surface. → Do not run screenshot work for a page while it is being changed; regenerate shots after the design settles, in the same change as the design.
    • A strict content security policy reported eval in both applications although nothing called it (2026-10-21) → zod 4 probes for Function("") inside a try; the browser reports the attempt even though it is caught. → z.config({ jitless: true }) in packages/assembly-model/src/schema.ts; prove a policy by loading the production build under it (tests/e2e/web-serving.spec.ts), never by reading the code. The terminal emulator writes <style> elements at run time, so both sites' policies allow inline style elements (the Console opens terminals too since 2026-10-21).
    • A Playwright test counted three loads where it expected two (2026-10-21) → the dev server runs React StrictMode, which mounts views twice. → Count requests from a baseline taken just before the action (image mirrors show the mode… in tests/e2e/fabric-console.spec.ts).
    • A shared terminal component spent its single-use ticket on a socket React closed at once (2026-10-21) → moving the Studio's terminal into packages/terminal made it a component that mounts with the ticket, and React StrictMode in development runs a fresh mount's effect twice; the stub saw two sockets; against the broker the first would spend the ticket and the second would get 401. In the Studio's old code the effect ran on a prop change of an already mounted component, so it never double-ran. → Effects that spend something single-use start it on the next task and cancel it in cleanup (TerminalScreen); the Console spec counts exactly one socket per session.
    • Tests broke when a fixture list grew (permission catalogue counts) → expected when you add to a shared fixture: update the counts in the same change.
    • "One primary button" tests failed after adding dialogs (2026-10-21) → FormDialog renders its children while closed, so a closed dialog's primary button counts. → Render a dialog's form only while it is open ({open && <form>…}), which also makes autoFocus work on opening.
    • A new field in an API response broke stubbed pages (2026-10-21) → the stubs in tests/e2e/identity-fixtures.ts (and screenshots.spec.ts) return the old shape, so the page read undefined. → When a response gains a field the UI reads, add it to every stub of that route in the same change.
    • A new header chip pushed the platform badge under it at 390 px (2026-10-21) → the Studio header's left group was shrink-0 whitespace-nowrap, so it could only grow sideways. → Header groups wrap (flex-wrap); a Playwright test opens the chip's panel at 390 px (studio-capacity.spec.ts).
    • ConfirmDialog never focused its Cancel button although the code called focus() (2026-10-21) → daisyUI's modal is visibility: hidden during its opening transition, and a hidden element cannot take focus; prefers-reduced-motion did not change that. → Focus dialog controls after the modal is visible (the dialog retries on the next frames, components/ui.tsx); assert focus with toBeFocused() (fabric-console-operations.spec.ts).
    • A form dialog's autoFocus field was not focused when the dialog opened (2026-10-21) → the same cause as ConfirmDialog: the field mounts while daisyUI's modal is still visibility: hidden. → Focus the first field with a retry on the next frames (useFocusWhenShown, views/Alerts.tsx); tests assert toBeFocused().
    • A spacing measurement reported a 492 px gap between sections (2026-10-21) → the capture had been trimmed by dropping middle sections, which leaves their space behind. → Trim only a contiguous run of subtrees from the top, or keep the whole page; re-read any gap finding against the trim.
    • TypeScript refused views/account/index.tsx next to views/Account.tsx (2026-10-21) → macOS file systems ignore case, so ./views/account resolved to the file and tsc reported "differs only in casing". → Never name a folder like a sibling file; the Console's credential pages live in views/credentials/.
    • Every accessible-name check failed for "Sign out" buttons labelled "Sign rita out of this sign-in" (2026-10-21) → axe's label-content-name-mismatch wants the visible text inside the accessible name (voice control users say what they see). → Start an aria-label with the visible words: "Sign out rita, signed in …".
    • A ticking "checked 12 s ago" inside aria-live would be read out every few seconds (2026-10-21) → live regions announce every text change. → Announce state changes (errors, stale data), never clocks; see the fabric-console skill.
    • Grouping the navigation broke a phone test on another page (2026-10-21) → visible group headings and a taller header added 40 px above every page on phones, pushing the directory rows' actions out of the first screen that toBeInViewport checks. → On phones the navigation stays one wrapping row with the group names for screen readers only (App.tsx); run every console spec after changing the shell, not just the new page's.
    • The sectors test failed axe colour contrast (1.62:1) on a dialog heading, every run, with nothing changed in the view (2026-10-28) → axe ran right after Save, while the closing modal was still fading out, and measured the half-transparent text. → Wait for the dialog to be hidden (await expect(dialog).toBeHidden()) before an accessibility scan; scan a dialog only once it is fully open or gone.
    • Servers tabs rendered as plain text, then failed axe (2026-10-21) → daisyUI styles .tab only as a direct child of .tabs (an li wrapper broke it), and its inactive tab colour is below 4.5:1. → Tabs are <a class="tab"> directly inside the nav.tabs, inactive ones text-base-content/75 (views/servers/Servers.tsx; axe in fabric-console-servers.spec.ts).
    • A deployed application's canvas said "Mock · Design only" with no live state (2026-10-25, found through the screens on the lab) → only the deploy dialog started watching the status, and the stubbed spec deployed and opened the canvas in the same page. → The designer starts watching a deployed application itself (ApplicationRoute.tsx). Every stubbed flow that matters also gets a step in tests/lab/ui.spec.ts, which reaches the screen the way people do (a link, a reload, the next day).
    • A worktree's Playwright run would have tested the main checkout's code (2026-10-25) → reuseExistingServer accepts any server on 5173/5174, and a dev server from the main checkout was still running. → Check which directory the server runs from before trusting a run, and give separate runs separate ports (ui-e2e.sh does).
    • A lab test sent "volumes": null to the worker (2026-10-25) → spec["volumes"].as_array_mut() on a serde_json::Value inserts the missing key as null before reading it (mutable indexing creates the entry). → Read an optional key with get_mut(…), never value[key] on a mutable value.
    • A test timed out clicking a "Try again" that had gone (2026-10-25, only in the full suite) → one switch made both stubbed endpoints succeed, and the servers panel re-read on its own before the test clicked its retry, so the error panel and its button vanished. → Give each stub its own failure switch and flip it just before the retry that should succeed; a panel that polls can recover between two steps (fabric-console-health.spec.ts).
    • "That token was not accepted" vanished now and then (2026-10-29, 1 failure in the full suite, 2 in 15 under load) → the sign-in check and the overview's own request were both refused for the wrong token; whichever came second ran onAuth again, found the token already cleared and set the reason to a bare sign-in page. → A refusal keeps the reason already shown (setAuthNeeded((shown) => shown ?? reason), App.tsx). To catch an ordering race, delay one stub and wait for its answer before asserting (fabric-console.spec.ts, token mode); passing on a single rerun proves nothing.

    Control plane and identity

    • The control plane refused a provider's token and logged nothing (2026-10-21) → refusals returned 401 without a log line. → Each refused credential is logged at warn as credential refused with method, path, credential kind, issuer and reason, never the token. It is not audited, since one row per bad request would let anyone fill the audit log.
    • A real provider issues 24-hour tokens; Apelora accepts at most one hour (2026-10-21) → provider defaults differ from our limits. → Document the limit next to the setting, configure the dev provider for one hour, and make the refusal reason visible.
    • A provider that is down at startup stayed refused until a restart (2026-10-21) → discovery ran only at startup and on save. → Retry unreachable providers every minute (auth_config::retry_unreachable).
    • An LDAP bind with an empty password succeeds (2026-10-21) → it is an anonymous ("unauthenticated") bind, not a failed one. → Refuse an empty password before connecting (ldap::sign_in; guarded by an_empty_password_is_refused_before_anything_is_sent).
    • ldaps://LDAP.Example kept its capitals after URL parsing (2026-10-21) → the url crate lowercases hosts only for special schemes (http, https, …), not ldap/ldaps. → Lowercase the host ourselves (directories::validate): the directory URL is its people's issuer, so its spelling must be stable.
    • The development directory's memberOf was empty (2026-10-21) → the memberof overlay does not run for offline slapadd. → The seed lists memberOf explicitly (infra/dev/directory/seed.ldif).
    • Any change to sign-in settings can lock everyone out → the API enforces the guards, not just the UI (lockout_guard, set_api_tokens, guard_leaving_local_accounts). Every new way in (local accounts, directories) must be counted by all of them.
    • extract(epoch …) came back as NUMERIC and failed to decode as f64 (2026-10-21) → PostgreSQL 14+ returns numeric. → Cast to ::float8 in queries that sqlx reads into floats.
    • A real control plane on the shared development database would have broken other checkouts (2026-10-21) → sqlx refuses to start when the database has a migration the binary does not know, and parallel sessions share apelora on port 15432. → For real end-to-end runs of a branch with a new migration, create a separate database on the same server (docker exec apelora-dev-db psql -U apelora -c "CREATE DATABASE …"), point DATABASE_URL at it, and drop it afterwards.
    • A new HealthState schema silently replaced the instance HealthState in the OpenAPI document (2026-10-21) → utoipa names schemas by the Rust type name only, so two types with one name collide without an error. → After npm run api:generate, check git diff packages/api-client/src/generated.ts for removed lines; give new schemas a distinct prefix (Health*, Capacity*).
    • Two people disabling the last two super admins at once both succeeded (2026-10-21) → the "last one" guard counted first and changed afterwards, outside a transaction; it also counted assignment rows, not enabled people. → Guards that keep "at least one" run the change and the count in one transaction under an advisory lock (identity::change_keeping_a_super_admin; containment_tests.rs races two requests).
    • A token or role could reach further than the person who made it (2026-10-21) → the escalation guard covered assignments only; tokens, revocation and legacy tokens (which skipped the route gate) had their own, weaker checks. → Every path that mints a credential or removes access applies the same containment (beyond_caller, check_revocation), and every caller passes the route gate.
    • A security review found guards that covered one path to an effect but not its neighbours (2026-10-25) → the escalation guard covered assignments but not joining a group or mapping one; group names matched without their source; the sign-in limit read the socket peer while the rate limiter believed trusted proxies; a terminal re-check skipped the sign-in that opened it. → When adding or reviewing a guard, list every path to the same effect (granting a role, naming the client, ending access) and give each the same check and its own test (containment_tests.rs, ADR 0016).
    • A persistence function generic over impl sqlx::Acquire broke tokio::spawn of the supervisor with "implementation of Send is not general enough" (2026-10-21) → the borrowed-lifetime bound cannot be proven for every lifetime inside a spawned future. → Take &PgPool, or &mut PgConnection for work inside a transaction (enqueue_job_in(&mut tx, …)); impl PgExecutor for single statements is fine.
    • A provider save audited reachable, which is only known after the settings reload (2026-10-21) → once the audit row moved into the change's transaction, the reload and the probes could only run after the commit. → In-transaction audit rows carry only what is known before the commit; probes run afterwards and their result goes in the response (auth_config.rs, directories.rs).
    • Worker test run_stops_on_shutdown failed now and then (2026-10-21) → a fixed 100 ms shutdown raced the heartbeat task when the machine was busy. → Wait for the observable condition (the worker's row) before shutting down (services/deployment-worker/src/lib.rs).
    • Parallel sqlx::tests asserting on a global metrics gauge would race each other (2026-10-21) → gauges are process-wide statics and tests run at once. → Assert on what the function returns (outbox::Pass); check the family's presence in the listener test (deployment-worker/src/metrics.rs).
    • npm run api:generate failed again for the first file download (GET /support-bundle, a tar) (2026-10-21) → the generator knew JSON and text only. → application/x-tar, application/zip and application/octet-stream map to Blob, and the client returns res.blob() (client.test.ts).
    • Widening the secret scan to every Apelora token prefix flagged an existing test's all-zero aps_ token (2026-10-21) → the scan greps source text. → Tests build token- and key-shaped values at run time (format!("aps_{}", "0".repeat(64)), a PEM label joined from words), so the scan stays strict.
    • Two handlers made #[derive(OpenApi)] fail with "storage_pools_config is defined multiple times" (2026-10-21) → utoipa names a path's generated config after the module path joined with _, so storage::pools collided with the existing storage_pools handler. → Name new handlers so module_fn cannot equal an existing handler's name (storage::pool_usage).
    • A generic schema name (Comparison) went into the OpenAPI document (2026-10-21) → utoipa names schemas by the Rust type only; a generic name would later collide silently. → Domain enums exposed through the API carry their area's prefix (AlertComparison, AlertSeverity); check generated.ts for generic new names, not only removed lines.
    • npm run api:generate failed on the first route that answers text (GET /metrics) (2026-10-21) → the client generator accepted only JSON responses. → The generator maps a text/plain success to string and the client returns the text (packages/api-client/src/client.test.ts guards it). A new non-JSON route needs the same treatment.
    • Failed terminal opens were never in the audit trail (2026-10-21) → the audit table accepts the outcomes success, denied and failed; the code wrote failure, the database refused the row, and a let _ = swallowed the error. A mutation test and a test of the real database found it, not the compiler. → Write audit outcomes through one set of constants or an enum, never free text; never discard an audit result with let _ = (log it, or refuse the action); a test of every outcome against the real table (sessions_tests).
    • A limit that refused a request had already spent the single-use approval it came with (2026-10-21) → the approval was consumed before the per-person cap was checked, so a person had to ask another person again. → Reserve the slot first, spend the approval last, and give it back (discard the reservation) if a later step fails (a_refusal_by_a_limit_does_not_burn_the_approval).
    • A session's timers and its terminate button stopped working while a client was stalled (2026-10-21; found by the security review, not a test) → the loop awaited a send to a browser that had stopped reading, and nothing else in it ran. → Every send in a long-running loop has a timeout, limits are polled first (biased), and the slot is released by a drop guard however the task ends.
    • The first review of the terminal feature found six holes the tests did not (2026-10-21) → the tests proved what the author thought of. → A read-only security review by a separate agent runs before a security feature is committed; give it the contract (secure-remote-access) and ask it to find what the code does not do.

    Incus (REAL INCUS TESTED behaviour that the documentation did not make obvious)

    • apelora-dns exited at once inside Debian and systemctl is-active returned 3 (2026-10-23) → the stub listener holds 127.0.0.53:53, and the kernel then refuses 0.0.0.0:53 (Address in use). The binary was fine; a direct run before the stub started was fine. → Turn the stub listener off in that instance (DNSStubListener=no), restart systemd-resolved when it is active, then start the unit. Run reset-failed first and ignore its status: a unit that has never failed makes it exit 1, and a crash loop otherwise hits the start limit so a later restart is refused even after the port is free (install_dns_resolver).
    • A later network.sync could not update the resolver: text file busy (2026-10-23) → the first attempt had already started the binary, then waited on another instance, and the retry opened that path with truncate. → Write apelora-dns.new and mv -f it into place; the running process keeps the old inode until systemctl restart.
    • The service name resolved and the instance name stopped after the client restarted (2026-10-23) → Debian's resolv.conf is the stub 127.0.0.53, so the resolver forwarded to itself, and dns.domain replaced the incus search domain the instance name lives in. → Drop loopback forwarders, read /run/systemd/resolve/resolv.conf for the real servers, and set dns.search to <application>.internal,incus.
    • Waiting on a copy operation was refused for the restricted identity ("permission for project default") → the operation is created in another project. → Fallback: poll the project's running operations for the names, then check that the target exists (copy_volume, project_operation_running).
    • Copied volumes lost their size and user.* labels → set them explicitly on the copy.
    • A refresh copy deletes the target volume's own snapshots and is accepted while the instance runs. Plan restores around that.
    • Moving an instance was refused → the project needs restricted.cluster.target=allow (now in scripts/test-cluster/up.sh).
    • Attached custom volumes do not follow a live-migrating VM unless marked dependent, which ties their lifetime to the instance. Design moves with that in mind (docs/design/mobility-and-ha.md).
    • A module's IPv6 traffic was refused although its connection was drawn (2026-10-22) → Incus gives an OVN network an IPv6 subnet even when the uplink has none, and an instance gets its IPv6 address about a second after IPv4. network.sync filled the address set as soon as any address existed, so the set held only IPv4 and nothing synced again. → When the network has ipv6.address, the sync waits for each reachable instance's IPv6 address (a_sync_waits_for_an_ipv6_address_that_comes_after_ipv4; scripts/test-cluster/ipv6.sh). After 60 s with IPv4 and no IPv6 the set keeps IPv4 and the sync succeeds (a_sync_stops_waiting_for_ipv6_that_never_arrives); otherwise a guest that never configures IPv6 fails forever and the job-failures alert stays on. Check every address family a network hands out, not only the one the uplink uses. Check every reachable instance in a replica slot, not the slot as a whole.
    • An IPv6 /64 cannot be a service range (2026-10-22) → enumerating 2^64 addresses is impossible, and IPv6 has no broadcast so the last address is usable. → APELORA_SERVICE_ADDRESSES accepts IPv4 /16–/30 (skip network and broadcast) or IPv6 /112–/126 (skip the subnet address), including comma-separated ranges of either family; each module still gets one address. Backends must match the listen family (/32 vs /128). Guard: service_ranges_skip_network_and_broadcast_and_reject_odd_input, a_sync_puts_ipv6_backends_behind_an_ipv6_service_address.
    • Giving the lab uplink (incusbr0) an IPv6 address wedged new OVN network creates (2026-10-22) → incus network set incusbr0 ipv6.address=fd42:198:18::1/64 on the live four-member cluster made incus network create … --type=ovn hang with no operation; systemctl restart incus is the same trap as before (SIGKILL incusd then start recovered). IPv6 service addresses only need ipv6.routes and restricted.networks.subnets. → Keep the lab bridge at ipv6.address=none; route fd42:198:100::/112 (ovn.sh). Guard: scripts/test-cluster/ipv6.sh.
    • mapfile is not on the macOS bash that runs lab scripts (2026-10-22) → macOS ships bash 3.2; mapfile is bash 4. Scripts that run on the workstation (not inside the VM) use a while read loop (scripts/test-cluster/ovn-ha.sh).
    • PEM files cannot be arguments to limactl shell (2026-10-22) → newlines split the remote command. Copy the files onto the VM and incus config set …="$(cat …)" there (ovn-ha.sh).
    • Debian's ovn-central.service is a dummy oneshot (ExecStart=/bin/true, 2026-10-22) → the databases are ovn-ovsdb-server-nb, ovn-ovsdb-server-sb and ovn-northd. systemctl enable --now ovn-central does not restart them. Package install starts empty local DBs before join options are written. → Write /etc/default/ovn-central first, restart those three units, and wipe the joiner DBs (ovn-ha.sh).
    • macOS LibreSSL openssl x509 -req signs with SHA-1 (2026-10-22) → Debian OpenSSL 3 refuses the leaf (ca md too weak) and OVN never loads TLS. The CA was SHA-256 because req -new -x509 defaults differently. → Always pass -sha256 when signing leaves (ovn-ha.sh issue).
    • A single-node OVN Connection of ptcp:<ip>:6641 is replicated to every raft member (2026-10-22) → joiners try to bind the first member's address and never listen on 6641/6642. → After the cluster forms, ovn-nbctl set-connection pssl:6641 and ovn-sbctl set-connection pssl:6642 (no IP: each member listens on all interfaces).
    • gh attestation verify printed the command list and every archive looked unverified (2026-10-26, Ubuntu's gh 2.45) → the subcommand arrived in 2.49. → Check the gh version first; with an old one, query the attestations API per digest (RELEASING.md), and say that the signature was not checked.

    • Simple Icons marks are not all CC0 (2026-10-25) → its metadata gives some marks Apache-2.0, CC-BY(-SA) or custom trademark terms, and our attribution file said CC0 for all. → Read the license field for each mark, record it in assets/logos/ATTRIBUTION.md, and use only CC0 or permissive marks for new classes (a test checks every bundled mark is listed with a licence).
    • A deployable NGINX showed twelve settings and applied one (2026-10-25) → only the image choice reached Incus; the rest were saved in the design, and the deploy-time fields arrived as SETUP_*/SECRET_* variables that the image never reads. Nothing on screen said so. → A runtime maps settings explicitly (command, environment), appliedSettings says which, and the Studio marks the others. Before making a class deployable, list what its image really takes and prove it inside the instance (CHECKS in scripts/runtime-requests.ts).
    • A new storage key nearly overwrote the custom modules (2026-10-25) → the catalog menu's open state was first given apelora.studio.catalog.v1, which already holds the custom module classes. → Grep for a localStorage key before choosing one; the menu state lives in apelora.studio.catalog-menu.v1 and an e2e test checks the custom-class key is untouched.

    Renames and compatibility

    • "an module" left behind after renaming "appliance" → the article sat before a line break. → Do renames with a regex that crosses line breaks, then grep .env.example, CITATION.cff, scripts and docs. Keep serde aliases and a migration for stored data.
    • A private struct still had the old field name → serde aliases go on every deserialised type, including private worker types.

    Secrets and evidence

    • Tokens must never reach the transcript, logs or screenshots → serve test tokens to the browser from a git-ignored file, revoke them when done, and delete any screenshot that shows one.
    • The audit log is append-only → when cleaning up test tokens, delete the token rows in their own statement. Never touch audit rows.
    • Label every result: MOCK VERIFIED, CONTRACT VERIFIED, REAL INCUS TESTED, or REAL-BROWSER TESTED against a named local service. Never round up.
    • A count written in prose goes stale (2026-10-21) → "fifteen built-in alert rules" stayed in three pages while the code had sixteen, and a first attempt to count them by matching the rule constructors missed one written as a struct literal. → Take a count from something the code already asserts (the test's RULES.len() literal), or generate the page (as for openapi.json and SETTINGS.md); don't copy numbers into setup text.
    • Example systemd units with a Documentation=file://… that is not on the runner fail systemd-analyze verify (2026-10-22) → the check copies the units and drops that line (scripts/ci/verify-install-examples.sh). Parsing is not the same as running them under a dedicated account on a production host.
    • nginx -t as the runner could not load the example TLS keys (2026-10-22) → the dummy keys are installed 0600 root:root, matching a host, and the GitHub runner is not root. On a host the NGINX master reads them as root. → sudo nginx -t (scripts/ci/verify-install-examples.sh).
