    Earlier design

    An earlier hypervisor-based design (a Rust node agent and a VM per module) was never built and was replaced by ADR 0001. Its documents and skill were removed on 2026-10-20; skills, agents, README, CLAUDE.md, SECURITY.md and the commercial licence drafts describe the Incus-first platform.

    What carries over unchanged

    • The whole Studio app and both packages. The Incus runtime is an addition to a module class (Phase 06), not a change to existing documents.
    • Port/terminal model, catalog rules, port placement convention, visual design contract.
    • Licence: AGPL-3.0-only for our code. Incus (Apache-2.0) and MAAS (AGPL-3.0, if adopted per ADR 0002) are used over their APIs.

    Known limitations

    • Incus 7.0.2 is what the lab runs. The LTS package 1:7.0.2-debian13-202610211947 was installed on all four members on 2026-10-23 (stand-by, then the other voters, database leader last). The first upgrade blocked the other three until they ran the same release; afterwards every member was Online on 7.0.2, with three database voters and one stand-by. The cluster was empty, so nothing was evacuated. Earlier evidence was produced on 7.0.1.
    • OVN HA and TLS (issue #13): scripts/test-cluster/ovn-ha.sh converts the lab's one database into three clustered northbound/southbound databases with TLS (APPLY=1, 2026-10-22, four members, OVN 25.03). REAL INCUS TESTED: raft had three members; stopping the leader's ovn-ovsdb-server-nb/sb elected another (term 3); 15 OVN ACLs on apelora-default were unchanged; Incus still listed 30 leftover module ACLs over ssl: remotes; a Debian container on that network pinged the OVN router (10.13.53.1) 5/5 with 0% loss during the outage. ovn.sh still starts the single-node plaintext shortcut.
    • One architecture (aarch64) on the test cluster: no mixed-architecture evidence.
    • IPv6: application-network rules and IPv6 service addresses (fd42:198:100::/112 on ipv6.routes) REAL INCUS TESTED 2026-10-22 (ipv6.sh). The servers' own cluster addresses stay IPv4. Do not set ipv6.address on the lab's NAT incusbr0 (it wedged network create until incusd was SIGKILL-started).
    • Member failure: OVN health checks cannot see a dead member, so a service address keeps sending a share of requests to its replicas there until Apelora substitutes them (APELORA_RECOVER_AFTER_SECS, default 120 s). Single-instance and stateful modules are recovered automatically only when all their disks are on the shared pool, and only after their member is fenced (about 140 s after its last lease renewal; ADR 0013); on member-local pools they wait for their member.
    • Publishing needs the network outside to route service addresses to the application network's router; the OVN router does not answer ARP for them.
    • Service names (DNS) are delivered with the service address (APELORA_SERVICE_NAME_<PROVIDER> = <module>.<application>.internal) and published on the application network. REAL INCUS TESTED 2026-10-23 (dns.sh) for the publication. The optional resolver module answers the names inside the application and forwards the rest. REAL INCUS TESTED 2026-10-23 (dns.sh): the restarted client resolved the service name to the service address, and the instance name still resolved. Without the module, OVN's own DNS still answers instance names only. An instance created earlier keeps the environment, and the DNS servers, it was given at boot (ADR 0004).
    • Changed images and settings (design, issue #48): each new instance records what it was built from (user.apelora.spec, since 2026-10-25). Deploying a version that changes a stateless module's image, settings or storage replaces its replicas one at a time (plan action replace, one application operation of kind update): each new replica (<replica>-u<n>) must pass its service's health check for 20 s before the old one leaves the service address and is deleted; one that is not healthy within 300 s stops the update, is deleted, and the rest keep serving (APELORA_UPDATE_*_SECS). Deploying an earlier version is the same path. REAL INCUS TESTED 2026-10-28 (demo.sh: two NGINX replicas replaced in 151 s, 0 of 6,864 requests failed); the stopped-update path is MOCK VERIFIED. Singleton and stateful modules are rebuilt in place (plan action rebuild, slice 3): stopped, their root disk rebuilt from the new image, given the new settings and started again, keeping name, member, address and volumes with their data; deploying needs confirmDisruption because the module is down meanwhile. The rebuild job is REAL INCUS TESTED (a container's volume data kept across Debian 12 → 13); the whole path through the API is MOCK VERIFIED. A change to a module's volumes is still not applied (kept, marked outdated). Instances created before 2026-10-25 have no record and are not compared.
    • Resources apply when an instance is created, and a later deployment resizes CPU and memory in place (instance.resize, REAL INCUS TESTED on a running container). Disk size is a separate volume grow. VMs, and a limit above the project's quota being refused by Incus, are not tested.
    • Health is Incus status plus the load balancer's TCP port check, with hysteresis; an application that hangs behind an open port is detected only for a module that declares a readiness command, and instances without a service address are not checked. Health trackers live in the worker's memory: after a worker restart they start over.
    • Load balancers while a member is offline (Incus 7.0): Incus refuses every load balancer create, update and delete in the cluster while any member is unreachable (peer node … is down; it notifies all members with a policy that needs every one of them, then reverts). A substitute replica then gets no traffic until the member returns or is removed (runbooks/member-failure.md). The worker recognises the refusal and records why, naming the member; the application's status carries it as trafficBlocked, shown in the Console and the Studio (MOCK VERIFIED; the refusal's text is the one seen on the lab). The upstream report is drafted for a maintainer to file. Updates may also drop the OVN health check (detected through the state endpoint and re-applied).
    • Evacuation and restore first take the replicas Incus will move out of their service addresses (instance_drains, network.resync, waiting at most APELORA_DRAIN_WAIT_SECS), and a moved replica rejoins once it runs and has its address. Before this, a share of a service's requests failed for up to about ten seconds (2026-10-25: 3 of 8 right after the member reported Evacuated). The supervisor no longer starts a replica Incus is still moving (issue #52): a stopped replica that carries volatile.evacuate.origin is left to Incus for 60 s first (REAL INCUS TESTED 2026-10-28: demo.sh fails a run in which the supervisor starts one, and none was started; the 60 s is a margin, not measured).     • Offline detection: in one drill Incus briefly reported a member that was not stopped as Offline; keep the recovery delay well above that (default 120 s).
    • Bare-metal provisioning (Phase 09): servers installed by hand are enrolled, held and admitted through Apelora; the MAAS adapter lists machines, fences through MAAS, and can commission and install an OS (cloud-init is sent and not stored).     A server fails (runbooks/member-failure.md)

    • Stateless replicas: REAL INCUS TESTED, 2026-10-20: a member's VM force-stopped three times with two members and three times with three members (demo.sh, recovery delay 30 s); replicas were substituted and later retired automatically; the service was whole again 84–206 s after the failure. In the one run where Incus refused every load balancer update for the whole outage, the service still became whole after about 3.5 minutes.
    • Stateless replicas, 2026-10-25 (Incus 7.0.2, OVN 25.03, four members, recovery delay 30 s, apelora-test-2 force-stopped for 5.5 minutes): not recovered. The substitute was created at t+53 s and running by t+78 s, but every load balancer update was refused (three syncs of five attempts each, peer node … is down), so the service address kept its two original backends. About half the requests failed for the whole outage. The dead replica's health check stayed online until t+78 s, then had no status, and OVN kept sending it traffic. Incus's code refuses these updates in 7.0.1 as well. A second run the same day (demo.sh, the same member force-stopped) explains the 2026-10-20 drills: every update was refused again, yet the service was whole after 60 s, because OVN's own health check took the dead replica out. Whether it does varies between runs; when it does not, the service stays degraded until the member returns, and the status says why (trafficBlocked, REAL INCUS TESTED the same day: named apelora-test-2 76 s after the failure and cleared once it returned). The member returned and the cleanup through the API succeeded.
    • Shared storage: REAL INCUS TESTED, 2026-10-21 (four members, Incus 7.0.1, clustered LVM pool shared on the lab SAN, scripts/test-cluster/ha-drill.sh, a container module with a 256 MiB volume): restarted on another member 144–155 s after its member's VM was force-stopped (three runs), only once that member's storage lease was dead, with its data intact. Per run (t = force-stop): Offline t+22/23/23 s; failure opened t+29/30/30 s; lease FAIL t+85/92/74 s; DEAD, fenced and recover job queued t+139/148/144 s; relinked at the same times; lock wait 7 s with 3 attempts / 5 s / none; running t+146/155/144 s. Run 1 was before the job waited for the lock; a fourth attempt was stopped before the failure because of a stale SSH host key. After run 3 the VM was started again: Online after 15 s, its lease LIVE with the next generation after 29 s, learned by the worker after 76 s, failure closed. In run 1 Incus also reported the three members that were not stopped as Offline for about 10 s (the heartbeat round was held up by the dead member); Apelora opened failures for them, saw their leases LIVE, fenced nothing and closed them.
    • Virtual machine on shared storage: HA_DRILL_VM=1, 2026-10-23, Incus 7.0.2, a debian/13 VM with migration.stateful=true, root disk and a 256 MiB volume on shared, three runs each force-stopping apelora-test-2. Running on apelora-test-1 at t+144/141/144 s; the file written beforehand read back at t+163/158/164 s; the stopped member Online again within 19 s, and the worker learned its new lease (generations 7, 8, 9) within 83 s. A cold start, on nested virtual machines, not a physical server.
    • BMC fencing: HA_DRILL_BMC=1 ha-drill.sh, 2026-10-21, REAL INCUS TESTED with the lab's lima provider standing in for a BMC: the member's Incus port was cut with nftables and its VM kept running; timeline as on the page; the restart job used 5 attempts and 26 Incus operations. The Redfish provider is CONTRACT VERIFIED only; the IPMI provider is CONTRACT VERIFIED only, and real_ipmi would be its first run on a real BMC.
